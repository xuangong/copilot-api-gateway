## Architecture and contracts

A manifest builder hashes actual on-disk inputs, builds each bundle, rechecks inputs, and emits a unique frozen manifest. A parent supervisor consumes that manifest and starts fresh unit processes. A unit owns its fixtures, Miniflare instances, append-only journal, stage deadlines and receipt. Physical readers are explicit per-variant adapters; the wire oracle remains independent of persistence validation. The aggregate reads durable rows and receipts and refuses incomplete collection.

Reuse the previous fixture and canonical readback logic after review; do not modify the previous harness. The prior readiness document is design evidence, not a completed measurement. See `../research/2026-10-01-resource-capacity-policy/workerd-readiness.md` for source locations and failure provenance.

## Evidence-driven matrix observation amendment

The initial reader incorrectly coupled physical collection to the absence of any deployed-baseline frame-value defect. Formal-01 preserved four real baseline capture failures: in Responses ingress translated from Messages (ok/tool/refusal/slow SSE), earlier created/in-progress frames retain an array reference subsequently populated with terminal items. Exact deployed source and independent original wire/R2 inspection agree; the immutable baseline must not be changed or these failures reclassified as success. Two unrelated reader bugs (null error metadata evaluation and protocol-specific renderer error shapes) are corrected separately.

The amended contract above allows a complete matrix to measure such failures while retaining them as failures and adding an independent fidelity regression gate. It is an explicit change to matrix observation qualification, not a case whitelist or retroactive qualification of Formal-01. Both failed outcomes remain unresolved unless their details are reviewed; the binary no-regression predicate does not claim equivalence of failure reasons. Counts, workload, resource windows, ordinary strictness, physical evidence, process ownership and no-deployment boundaries do not change. Every new execution requires the amended spec/tooling to be frozen with a fresh canary and formal run.

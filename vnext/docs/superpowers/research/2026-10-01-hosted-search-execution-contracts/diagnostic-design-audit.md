## Recommendation

Do not enable active-queue shedding, publication rejection, or coalesced notification replacement under a claim of transparent recovery. Current durable storage supports bounded pages and point lookup, but the current Dashboard does not recover an arbitrary notification gap. No existing numeric policy justifies a queue or publication cap.

A small, production-path improvement is available now: make the dump SSE route own request cancellation before subscribing/reading its initial SQL snapshot, including an already-aborted signal and cancellation during the snapshot read. This closes a concrete active-subscription lifetime gap without changing persisted data, live event names, or the existing meaning of cancellation. It does not bound a connected slow consumer or aggregate publication work.

If a further publication contract step is desired, distinguish storage settlement from notification settlement inside the existing terminal owner. Preserve all current writes and notifications. This can make an already-committed row explicit when its notification fails; it is an ownership/error-classification improvement, not admission or reconciliation. An unused prepare/start/cancel facade or an always-admit policy would not close the capacity gap.

## Exact existing clients and recovery behavior

1. **Gateway SSE adapter:** `control-plane/dump/routes.ts:102-139` subscribes before fetching the latest 100 rows, sends `snapshot`, then sends one `appended` per metadata notification. Subscribe-before-snapshot protects same-broker publications during that SQL read. It also means notifications accumulate while SQL or `writeSSE` is slow. No SSE `id`, `Last-Event-ID` handling, resume token, or gap/reload event is present in this route.
2. **Dashboard Requests panel:** `vnext/apps/dashboard/src/tabs/requests/RequestsPanel.tsx:22-57` uses `useDumps`. The hook first fetches a 25-row page, then opens `EventSource`; snapshot and appended handlers merge by record ID and sort all retained rows (`state/dumps.ts:9-14,36-47,61-98`; `api/dumps.ts:35-41`). It has no explicit reconnect loop; it relies on browser EventSource reconnect behavior. Each new server stream reads another latest-100 snapshot.
3. **Dashboard errors and history:** `error` only sets “Live updates disconnected. Reconnecting…”. Any later valid snapshot or appended record clears that state. There is no persistent history-incomplete status, replay acknowledgement, periodic refresh, or automatic gap scan (`state/dumps.ts:76-98`). “Older” follows the cursor from REST pages; SSE snapshots do not update that cursor (`:45-47,155`). Detail and export are independent point reads (`:113-148`). Closing/reopening the panel restarts paging and streaming; merely receiving a snapshot does not replace all retained state.
4. **Inference clients:** HTTP responses receive preallocated `x-dump-record-id`/`x-dump-key-id` correlation headers before persistence completes (`shared/dump/accumulator.ts:169-182,485-493`; Responses turn `data-plane/chat-flow/responses/turn.ts:312-319`). No production in-repository consumer of these headers was found. They are not a commit receipt. Native Responses WebSocket sessions open per-turn dumps (`responses/session.ts:189-196`), then send response events (`:210-230`); the shown path does not send `turn.ready.headers` as per-turn dump acknowledgement. A new refusal contract cannot assume all HTTP and WS users have an existing receipt UI.

### Why snapshot reconciliation is incomplete

The current list API provides only `before` and a page limit (`shared/dump/store-contract.ts:8-11,25-27`). SQL resolves `before` to the row's `created_at`, returns older `(created_at, id)` tuples, and returns an empty page if the cursor row is gone (`repo/dump-store.ts:394-423`). That is ordinary history pagination, not a persisted delivery cursor.

If a gap contains more new records than the reconnect snapshot covers, merging that snapshot leaves a middle gap. Existing “Older” paging may start below the pre-gap REST cursor and never traverse that missing middle. The UI clears its error anyway. Even a new “page until the previous top ID” loop would not prove complete recovery: IDs are allocated at request start; `created_at` stores terminal `completedAt` before preparation/upload/SQL settlement (`accumulator.ts:182,503-549`; `dump-store.ts:308-317`). Commit order can differ from both keys. A late commit can land behind an already-scanned boundary. Retention and cursor deletion add another boundary.

Therefore “the row remains stored” and “the client has reconciled every missed notification” are different claims. A full retained-history scan would also introduce potentially unbounded SQL work and Dashboard retention; it is not a free queue replacement.

## Minimal alternatives

| Alternative | Exact behavior consequence | Assessment |
| --- | --- | --- |
| **Bind SSE request cancellation before snapshot work** | The actual route's controller observes the raw request signal during initial read, so its existing broker subscription cancels promptly when that signal aborts. An already-aborted request need not allocate a subscription or start a snapshot read. | Recommended narrow improvement. No threshold, data format, normal FIFO, or successful-client behavior change. Does not cancel an already-started SQL operation by assertion. |
| **Separate store commit and notification outcomes** | Keep the current SQL-before-notify chain; report a committed record with notification failure distinctly from storage failure. Capture metadata/ID rather than body records in the notification continuation. | Safe internal production wiring if consumed by the existing failure/reporting owner; preserve best-effort behavior and do not return inference failure or add an automatic retry. No resource-bound claim. |
| **Explicit prepare/start/cancel owner for publication** | To prevent work, admission must precede the work it claims to bound. Before-start cancellation can release only not-yet-started private work; after-start cancellation must retain actual preparation/upload/SQL settlement ownership. | A useful future boundary, but enabling cancellation/rejection of a dump creates missing records. Policy and a client-visible outcome are still required. A start wrapper at terminal `put` is too late to bound constructor preparation, and `waitUntil` cannot serve as admission. |
| **Reject/disconnect a slow subscription and rely on existing reconnect** | Queue state disappears and latest snapshot may omit notifications. The existing UI presents the gap as resolved after a valid snapshot/appended event. | Not safe as a transparent lossless change. Requires an overflow policy and a persistent client reconciliation state; normal graceful channel close currently drains and must not be repurposed silently as queue discard. |
| **Coalesced wake-up followed by latest-page reload** | Replaces one event per committed metadata row with “the stored view changed”; a dirty flag can coalesce redundant wake-ups without an arbitrary numeric queue size. | Valid only as a deliberately different view contract. Latest-page replacement loses access to already-loaded visible history; merging preserves old data but does not fill gaps. Both require explicit UI semantics. Current `appended` listeners cannot consume a new wake-up event. |
| **Wake-up followed by complete catch-up** | Re-read durable state after each dirty generation, with single-flight loading and dirty-during-load handling. | No existing safe catch-up boundary: current cursor is not commit-monotonic, retention can remove anchors, local wake-ups miss other isolates, and full scans/retained unions create separate resource domains. Do not implement as a small broker substitution. |

The first alternative should wire one request-owned cancellation listener before any subscription/snapshot phase, check the already-aborted state, and remove that listener on every success/failure/cancellation exit. Preserve eager registration before SQL for live requests. If abort occurs during an already-started SQL read, cancel the subscription immediately, suppress subsequent SSE startup/delivery for that aborted request, and let the existing read settle; the store has no SQL-cancellation port. This is a source-level ownership finding, not a browser disconnect timing measurement. The present listener is installed only inside the later `streamSSE` callback (`control-plane/dump/routes.ts:108-122`), leaving no propagation from `c.req.raw.signal` to the subscription controller during the awaited snapshot.

### Focused future verification for the cancellation follow-up

These are proposed cases, not tests run in this audit:

1. An authorized already-aborted stream request must not register a live subscription or begin its snapshot read after the route observes cancellation.
2. Hold an otherwise valid snapshot read pending, publish a frame, then abort the raw request. Assert subscription termination and buffered-frame disposal before the read settles. Subsequent publications must not reach that subscription. Settle the SQL read afterward and assert no snapshot/live delivery starts for the canceled request; do not claim the SQL operation was canceled.
3. Fail the pending snapshot read without client abort. Preserve the route's existing failure behavior while releasing the subscription and raw-signal listener exactly once. Also cover abort followed by snapshot rejection to avoid an unhandled rejection or duplicate terminal action.
4. For a live request, publish during the held snapshot query and then resolve it. Confirm snapshot followed by queued appended metadata, including harmless duplicate IDs that the Dashboard already merges. Complete/abort the streaming response and verify listener cleanup. This guards the subscribe-before-snapshot guarantee while moving cancellation wiring.

Implement these at the route/owner boundary using controllable read settlement and the real broker behavior, plus the existing route authorization coverage. They do not require a throughput benchmark or a queue threshold. Keep this as a separate follow-up if the current batch is limited to hosted/search execution contracts.

For the prepare/start/cancel option, do not confuse canceling the **live notification** with canceling **durable publication**. After SQL commit, canceling notification needs an observable visibility-gap policy; it cannot recast the row as not committed. Before SQL commit, rejecting metadata work means the existing payload-omission field is insufficient, because that field itself requires a stored row. Metadata-only fallback cannot solve exhaustion of metadata capacity. A no-wait admission decision also must not grow an implicit list of waiting closures retaining full records.

## Blockers for actual overflow/admission

- Choose whether the live contract is every admitted notification, a latest retained view, or an explicitly incomplete history that the user can reload. The current UI implements none of the required overflow states.
- Define what is bounded: metadata items, metadata bytes, active publication operations, subscriber count, SQL reload work, and client history are separate owners. Existing capture estimates and list page sizes are not substitutable policy values.
- Define observable notification overflow independently from not-admitted diagnostic persistence. Keep inference status separate. Account for HTTP correlation headers and native WS clients, not just the Dashboard.
- For lossless retained-history recovery, provide a credible durable visibility/resume boundary and define retention/cursor-loss behavior. Current `before` pagination and local broker wake-ups do not supply one. No persisted-format change is selected by this audit.
- Define old-client behavior before new SSE events or discard policies: old Dashboard clients ignore unknown events, and their generic error clears on the next successful frame. A versioned/negotiated mode or coordinated compatible rollout would be a design requirement, not evidence that recovery already exists.

No production cap, rejection policy, new numeric constant, persisted format, migration, or performance claim is recommended by this audit. The direct cancellation wiring and separate publication outcome classification are reviewable contract improvements while the substantive active-capacity policy remains open.

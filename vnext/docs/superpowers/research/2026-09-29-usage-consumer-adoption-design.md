# D08 consumer adoption: sequential implementation briefs

Date: 2026-09-29. **Historical design alternative, not the adopted C2-C6 implementation.** This source-only brief originally proposed the sequence below. The later C2 candidate passed its 32-case oracle but failed the full-load cost gate after three correction rounds; its endpoints were removed from the accepted product, and C3-C6 were skipped/deferred without implementation. See the [C2 evaluation](2026-09-29-usage-projections-evaluation/README.md). The accepted overview API, quota consumer and legacy detail repairs are documented separately. Paths below are relative to `vnext/` unless prefixed with the work directory.

## Recommendation and boundaries

Ship C1 first: the selected key's monthly quota panel is an independently useful real consumer and needs only a full total. Then build bounded projections and migrate Usage one selector family at a time. Keep the legacy detail API available. Do not construct pretend `UsageRow[]` from overview pages.

The default design preserves every category, chart series and existing control. Pagination is a transport mechanism; it is not a new top-N UI. Each response is bounded, but fetching every category necessarily leaves total download, client memory, and rendering proportional to category/series cardinality. A global cap would change behavior and requires a separate product decision. No global new UI or shared-owner picker is part of these packages.

## C0 — Foundation release gate (root-owned)

Accept the two review fixes before C1: fixed-count owned/assigned-key scope lookup, and a non-cancelling unresolved known-dimension row count after historical price fallback (including zero-quantity rows). Current repo source calls this `unpricedDimensionRows`; consumers must follow the final reviewed wire name. Signed `unpricedTokens === 0` cannot establish completeness. Wire metadata must survive total/bucket/breakdown adapters. Require actual session/API-key/grant HTTP tests, assigned-only large-key workerd coverage, existing oracle parity, and independent review. This document does not certify them.

## C1 — Adopt overview total in selected-key quota (first deliverable)

**User outcome:** selecting a key still displays the same UTC-month requests, weighted tokens, cost and percentages while downloading aggregate rows instead of every hour/model/client identity. UsageTab remains unchanged.

**Files:** `apps/dashboard/src/api/keys.ts`, `apps/dashboard/src/state/keys.ts`; introduce focused `state/key-quota.ts` and `state/key-quota.test.ts` for pure projection; extend `api/usage.test.ts` or add `api/keys.test.ts`. Reuse the reviewed `api/usage.ts` overview types and helper. Thread a narrow quota load state through `tabs/keys/KeysTab.tsx`, `KeyDetailPanel.tsx` and `QuotaEditor.tsx` (plus existing translation files if needed). No gateway change is required for this first consumer.

**Contract:** add `getMonthUsageTotal(keyId, now = new Date())`, using exactly the existing UTC month construction: first UTC hour of current month inclusive through first UTC hour of next month exclusive. Call overview with `key_id`, `bucket: "day"`, `axis: "key"`, `limit: 1`, no `as_user`. Read only `total`; neither buckets nor the one category row form the denominator. A UTC calendar month is at most 744 hours, so `hour` also fits, but `day` reduces redundant payload to at most 31 buckets. The first package still pays three aggregate statements; total-only optimization is a later C2, not a reason to delay useful adoption.

Project `reqUsed = total.requests`, `tokenUsed = computeWeightedTokens(total.cacheRead, total.cacheCreation, total.input, total.output)`, `costUsed = total.costUSD`. The shared formula is linear (`0.1, 1.25, 1, 5`), without per-row rounding, so aggregating first preserves arithmetic within floating tolerance. Preserve existing quota limits, percent rounding, null/zero-limit behavior and cancellation on selected-key changes. Keep the overview price metadata with the result; do not relabel recorded cost as complete billing or null prices as free. The panel must not describe recorded cost as a complete bill; retain the non-cancelling unresolved-price metadata for that distinction.

**Authorization:** do not derive admin scope from current keys, broaden an assignee's scope, add a user-supplied `ownerId`, or drop selected `key_id`. Admin can select any permitted key; sessions can select owned/assigned keys; out-of-scope key IDs yield the current empty result semantics. API-key auth remains bound to its credential even if `key_id` names another key or a session is also present. Explicit shared viewing is not used by Keys. The broader overview route's grant behavior remains covered by foundation tests.

**Regression acceptance:** real-SQL detail adapter + old reducer versus overview total on identical month fixtures: 28/29/30/31-day months, Dec/Jan transition, exact exclusive end, all six billing dimensions, multiple upstream/modelKey identities, request-only/token-only rows, explicit zero/null/fallback prices, signed imported quantities, empty month, large assigned scope. Counts exact; weighted and cost tolerance `max(1e-12, abs(expected)*1e-10)`. Exercise percentage boundaries to expose observable floating rounding differences before accepting parity. The existing enforcement oracle is `packages/gateway/src/data-plane/observability/quota.ts`: it reads repo records directly, includes image input/output, applies the same weights, and calls `recordCostUsd`. Compare that path separately on normal and signed/negative fixtures: old dashboard positive display projection and raw enforcement arithmetic need not be identical for imported negative data. This adoption promises existing dashboard display parity, not a newly unified enforcement total. Do not change quota-enforcement math or query in this UI package.

**Browser acceptance (isolated fixture only):** select owned then assigned keys; switch A→B before A finishes; confirm B's numbers cannot be overwritten; deselect; edit quota limits; exercise failure and empty month; local/UTC Usage preference must not alter quota month. Network must show overview and no selected-key detail fetch. Replace the current zero-on-failure fallback with an explicit quota-only `idle | loading | ready | error` state. Loading/error preserves the last valid same-key result when available, clearly marked stale; otherwise render used values and percentages as unavailable; never carry A values into B. A successful empty total alone may render zero. Preserve editable limits and provide a scoped retry. This is a deliberate narrow correction needed to avoid presenting a failed aggregate as known-zero usage, not a global UI redesign. Test errors, retry, stale completions and real empty success separately.

**Done:** real quota consumer uses overview, focused checks and package typechecks pass, root `ci:local` passes, screenshots only if UI actually changes. Do not claim full D08 adoption. If C0/C1 alone land, this is a useful stopping point.

## C2 — Projection contract and traversal consistency prerequisite

**Files:** `packages/gateway/src/repo/types.ts`, `repo/usage-overview.ts` (factor reusable pricing/scope SQL without changing the detail oracle), new `repo/usage-projections.ts`, `repo/shared/repos.ts`, `control-plane/token-usage/routes.ts`, `apps/dashboard/src/api/usage.ts`; new real-SQL projection/route tests alongside `tests/control-plane-token-usage*.test.ts`.

Add separate narrow projection endpoints/methods, rather than repeatedly computing an overview's total and buckets for every category page:

- `total`: the reviewed metric object for the full filtered range, one aggregate statement.
- `facets`: one requested raw axis, range and authorized scope only, page size <=200; no active filters. Key rows include existing names/fallbacks and enough visibility-safe participant metadata to reconstruct `buildDimensions`.
- `distribution`: one selected axis and active filters, <=200 categories; denominator is the separate full total, never this page. Incoming-to-routed mapping is a separately paged set of raw pairs, not `GROUP_CONCAT` or a truncated nested array.
- `time`: full filtered UTC-hour totals, <=744 hours per request, no category payload.
- `series`: selected axis × UTC hour; page series identities, never flattened cells that split a series unpredictably. Enforce `hours * seriesLimit <= 744` as a concrete starting response bound; for example 168 hours × 4 series. Return a series catalog and its sparse hour cells plus continuation. A zero-metric record still has presence.

All reuse the exact foundation accounting projection and server-resolved authorization. Add `user_id` as a filter only with explicit route authorization and existing participant visibility semantics; it selects entire keys the user can reach and intersects other filters. It does not attribute individual requests. `user` grouping means the identical participant-set identity and label from `usageAttribution`, including unknown/deleted-key `_admin` fallback. Resolve key→group in fixed-count queries, not N lookups; do not multiply shared-key metrics across people. Share a pure attribution helper or exhaustive parity fixtures instead of recreating an owner-only SQL shortcut. `as_user` on every new route must independently recheck the session grant; shared key refs and filters remain HMAC scoped. No shared Usage picker is introduced.

### Traversal consistency contract (root decision)

Use keyset cursors over raw identities (encoded tuples, no delimiter collisions), bound to range/filter/auth/projection. Shared-key cursors must be opaque or authenticated encrypted tokens so raw key IDs do not leak. The foundation offset cursor remains its documented API contract; new traversals must not reuse it. Keysets avoid offset shifts and guarantee every category is returned exactly once for unchanged data when all pages are traversed. They do **not** provide a point-in-time snapshot: active writes can insert categories before the cursor, remove categories, change metrics across pages, or make totals and tables represent different instants.

Root explicitly accepts eventual consistency consistent with the existing live dashboard and foundation. Document it in API types and implementation reports. “Complete” below means exhaustive traversal with no deterministic limit/truncation on unchanged data, never a cross-request snapshot guarantee under active mutation. Do not add global revision triggers, schema migrations, write amplification or a snapshot protocol for this adoption.

Accumulate each range/filter/auth generation privately, cancel or ignore superseded requests, and publish a finished traversal atomically. This prevents mixed client selections, not mixed database instants. On failure retain clearly identified previous same-scope data or show an error; never publish an unfinished page set as the new result. Refresh restarts from the first page and can discover categories inserted behind an earlier cursor. Recheck current authorization/grants on every request; cursors are not authorization. Concurrent mutation tests must show no offset-shift duplication, stale selection overwrite or security widening and must explicitly capture the permitted new-earlier-category and mixed-time-total limitation. Do not imply a refresh guarantees an instantaneous snapshot either.

For C2's additive endpoints, run SQL parity, authorization and local workerd tests; measure statement count, returned rows, serialized bytes and rows-read on owned AND assigned high-cardinality fixtures. Fixed output bounds do not imply bounded scan work. No production-performance claim follows from source inspection.

## C3 — Complete catalogs and filtered summary

**Files:** `state/usage.ts`, new `state/usage-projections.ts` (pure request planning/reducers) and tests, `tabs/usage/participants.ts`, `tabs/usage/UsageTab.tsx`, `api/usage.ts`. Do not redesign `UsageFilters.tsx`.

Introduce one request generation keyed by range, zone, auth scope and refresh nonce; catalog requests exclude active filters, while total requests include all filters. Fetch all facet pages into a private accumulator; publish only complete catalogs. Keep missing routed/client values excluded from dropdowns as today; retain the legacy incoming option and raw empty-string identity. Sort client/model/incoming using the same JS ordering and keys/users using existing locale/name ordering. Participants cover only authorized visibility; admin users derive from keys with usage, not every user or every current key. Preserve independent dropdowns and `sharedInScope` notice.

Migrate summary to the full total and `hasRecords`; retain main detail for distribution/chart temporarily. Distinguish unfiltered range presence (replaces `data.length` for existing hint/empty state) from filtered total presence. Request-only and observed-zero rows are records. No positive-cost/tokens test substitutes for presence. Filters should not make their own available options disappear. A failed/stale projection must not overwrite a newer generation or display zeros as a successful answer.

Acceptance: full selector oracle including conflicting filters, empty incoming model, real names equal to localized fallback labels, NUL strings, deleted admin keys, assigned keys and full participant-set grouping; overlapping loads and refresh; summaries cannot use a categorical page. This intermediate state may increase requests and still downloads detail: call it a parity seam, not a measured bandwidth win. Use C2 eventual-consistency and client-generation rules; do not claim these projections share a database snapshot.

## C4 — Distributions with complete denominators and mappings

**Files:** `state/usage-projections.ts`, `state/usage.ts`, `state/usage-model-dimensions.ts`, `tabs/usage/UsageDistributionTable.tsx` only if changing its prop contract, and focused tests.

For each unselected dimension, traverse distribution pages fully; for incoming model, traverse mapping pairs fully as well. Preserve existing hide rules (including incoming `null` versus `""`) and full six metrics. Rebuild final tables with existing descending-total-tokens sort and locale-label tie order; binary API page order is not display order. For key/user names use the complete same-generation catalogs. Preserve existing client/chart fallback grouping, even where it differs from routed-table identity; any collision cleanup beyond current incoming/routed identity tests is separate behavior work.

Publish complete tables and legends atomically. Percentages may continue using complete rows, or accept an explicit full denominator; never sum the loaded page. Incoming routed labels retain the current distinct-label and sort semantics, with every routed model reachable. Use raw identities internally, then existing localization; do not merge legacy incoming and a real model with the same rendered label.

Acceptance: >200 categories and >200 routed mappings for one incoming model, tie sorting, shared participant groups, mapping labels that collide, zero denominators, signed costs, changes during traversal and cancelled requests. Browser hover/legend/stacked bars and rows must describe the complete dataset. Default transport paging has no “first page looks final” state. Explicit visible pagination would require revising bars/legend/denominator presentation and is not assumed authorized by this design.

## C5 — Chart projection and main-detail removal

**Files:** `state/usage-projections.ts`, `state/usage.ts`, `state/time-buckets.ts` (prefer reuse), `tabs/usage/UsageTab.tsx`; `components/TimeSeriesChart.tsx` should require no presentation change.

Preserve the existing first unfiltered axis: admin user → key → client → routed model → total; incoming filtering does not alter this priority. For grouped mode, traverse every series page and UTC-hour chunk under C2 eventual-consistency and client-generation rules, then rebucket with `utcHourToBucketKey` and `zoneOps` in the browser. For total mode use `time`. Carry per-series cost and all cache metrics; cache line is the full filtered cache sum, not a sum of an incomplete set. Both request and token plots use the same fetched metrics. Keep zero-fill bucket labels, daily positive-point navigation, history/back behavior, and legend identities/order against the existing selector oracle. If current series order depends on detail row order, establish its deterministic source order before switch; do not silently substitute binary category order and change color assignment.

**Time limits:** do not force local months through a single 744-hour request. A 31-day local month crossing fall-back can span 745 UTC hours. Partition the exact existing `[start,end)` query into adjacent <=744-hour chunks (smaller chunks for grouped cell budget); sum no boundary twice. Leave current UTC-hour truncation and local half-hour/quarter-hour behavior intact. Keep current DST chart labeling, including its repeated/skipped local-hour behavior; this project changes aggregation transport, not date UX.

Acceptance: complete grouped results beyond a page, all axis/filter combinations, tooltip cost, full cache line, day drill/back, UTC and local spring/fall DST, 31-day fall month, Asia/Kathmandu and half-hour zones, unknown series names, empty chart with recorded-zero rows, rapid mode/range/metric changes. Main detail call can be removed only after C3–C5 match the oracle. Remaining strip detail is explicitly tracked, not called full adoption.

## C6 — Strip and forecast, without a new timezone SQL engine

**Files:** `state/usage.ts`, `state/usage-projections.ts`, existing `state/usage-strip.ts`, `state/usage-forecast.ts`, their tests and `tabs/usage/UsageTab.tsx` acceptance coverage.

Smallest exact replacement is complete UTC-hour `time` totals split into <=744-hour requests for the existing `computeStripRange` (roughly 117 days, normally four requests). That leaves a bounded roughly 2,808-hour client result, independent of model/key/client cardinality. Reuse browser day rebucketing and `buildRollingStrip`; this avoids claiming SQLite UTC-day groups support IANA zones. A later daily endpoint may use an explicit validated hour→day plan or tested server IANA semantics, but is not required for useful full adoption.

Apply all filters on the server, including participant user filter. Cache keys must now include filters, scope, zone, exact range and generation: the old cache held unfiltered detail and cannot be reused unchanged. Pinned endDate remains excluded because selecting a cell does not move the strip. Refresh invalidates both main and strip data; switching tokens/requests must not discard cost/token strip work. Preserve 90 trailing-28-day cells, coloring, hover, selected ring, and forecast inputs.

Acceptance: old detailed-hour oracle versus new hourly totals through DST/UTC/local zones; all 90 cells and forecast output; pinned selection, returning to 28d, filter changes, refresh, errors and stale completion. Missing-hour zero behavior and completely empty-range behavior must stay distinct where current helpers distinguish them. Remove the strip detail request only after parity passes.

## Root decisions, costs and final acceptance

1. **Proceed independently with C1 after C0.** Recommended; no Usage UX or snapshot decision blocks it. C2 total-only can later remove its redundant bucket/category scans without changing the consumer result.
2. **C2 consistency is decided:** keyset traversal, eventual consistency during active mutations, atomic per-client-generation publication and cancellation. Full unchanged-data coverage is required; cross-request point-in-time completeness is not promised. No global revision trigger, migration or snapshot gate is approved.
3. **Accept all-pages transport to preserve current UI.** Recommended for semantic parity, with cancellation and atomic completion. Total browser memory remains unbounded by category count; no claim that a 200-row HTTP bound solves it. If this cost is unacceptable, require a separate visible pagination/series-navigation design before removing detail.
4. **Prefer chunked UTC-hour totals over new timezone aggregation initially.** This preserves current date math and handles 745-hour months and the strip without widening the foundation cap. More requests are an explicit cost.

Each package is a separately reviewable change with real-SQL tests for backend logic, pure selector tests for hooks, and isolated browser acceptance for a consumer switch. Reuse existing usage adapter/model/range/participants/strip/forecast suites; run package typechecks and root `bun run ci:local` after integration. Record request/query counts and bytes before/after on the same synthetic fixtures; review D1 rows-read amplification and page/request amplification. No live data is needed. No install, push or deployment is implied.

Full consumer completion means Keys quota, summary, independent catalogs, all distributions and incoming mappings, participant user semantics, complete grouped chart, and rolling strip/forecast no longer depend on detail while matching the existing selectors and auth rules. Keep the compatibility detail endpoint unless separately authorized to remove it. A merged foundation or migrated quota panel alone must not be reported as full UsageTab adoption.

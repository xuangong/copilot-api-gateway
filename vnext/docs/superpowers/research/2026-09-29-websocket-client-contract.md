## Wire contract established by pinned first-party source

1. **Selection and handshake.** This Codex uses Responses WS only when `model_provider.supports_websockets=true` and the session has not switched to HTTP fallback ([client.rs L1046-L1058](https://github.com/openai/codex/blob/8ff74cc9b11ac54c4c4446ef60a87b49ae657a1f/codex-rs/core/src/client.rs#L1046-L1058)). The client builds a WS URL for the Responses endpoint, sends provider headers plus auth headers during HTTP upgrade, and uses one connection across turns ([responses_websocket.rs L390-L420](https://github.com/openai/codex/blob/8ff74cc9b11ac54c4c4446ef60a87b49ae657a1f/codex-rs/codex-api/src/endpoint/responses_websocket.rs#L390-L420)). Its custom-provider default is false; OpenAI built-in is true ([model-provider-info L145-L147, L418, L453](https://github.com/openai/codex/blob/8ff74cc9b11ac54c4c4446ef60a87b49ae657a1f/codex-rs/model-provider-info/src/lib.rs#L145-L147)). Current C11 disables gateway-generated custom config/catalog WS claims. A `426` upgrade response triggers immediate session HTTP fallback; a generic `404` enters the normal retry/error path, so `426` must be scoped to a real attempted Responses upgrade, without changing ordinary GET semantics ([client.rs L1803-L1825](https://github.com/openai/codex/blob/8ff74cc9b11ac54c4c4446ef60a87b49ae657a1f/codex-rs/core/src/client.rs#L1803-L1825), [loopback fixture](https://github.com/openai/codex/blob/8ff74cc9b11ac54c4c4446ef60a87b49ae657a1f/codex-rs/core/tests/suite/websocket_fallback.rs#L34-L88)).
2. **Inbound turn.** The JSON text message is a flat `{"type":"response.create", ...Responses create fields...}`. In this Codex source, the serialized body includes `model`, `input`, `store:false`, `stream:true`, `tool_choice`, `parallel_tool_calls`, and optional `instructions`, `tools`, `reasoning`, `stream_options`, `include`, `service_tier`, `client_metadata`, `previous_response_id`, `generate` ([common.rs L302-L386](https://github.com/openai/codex/blob/8ff74cc9b11ac54c4c4446ef60a87b49ae657a1f/codex-rs/codex-api/src/common.rs#L302-L386), [client.rs L1844-L1873](https://github.com/openai/codex/blob/8ff74cc9b11ac54c4c4446ef60a87b49ae657a1f/codex-rs/core/src/client.rs#L1844-L1873)). Accept its `stream:true` for wire compatibility and avoid forwarding transport-only fields to HTTP upstream. No `stream_id` or `event_id` appears in this Codex serializer. Official OpenAI Docs now specifies `stream_id` multiplex/forks and says `stream`/`background` are not used; this is a **documented broader mode versus this pinned Codex wire variant**, not evidence to claim full upstream WS support ([official WebSocket Mode](https://developers.openai.com/api/docs/guides/websocket-mode.md)).
3. **Outbound frames and terminal.** Emit individual JSON Responses events as WS text frames, not `data:` SSE strings. The pinned reader parses `response.created`, output events, and ends its per-request read only on `response.completed`; `response.failed` and `response.incomplete` are errors. EOF/close before completion is an error ([responses_websocket.rs L689-L838](https://github.com/openai/codex/blob/8ff74cc9b11ac54c4c4446ef60a87b49ae657a1f/codex-rs/codex-api/src/endpoint/responses_websocket.rs#L689-L838), [sse/responses.rs L353-L500](https://github.com/openai/codex/blob/8ff74cc9b11ac54c4c4446ef60a87b49ae657a1f/codex-rs/codex-api/src/sse/responses.rs#L353-L500)). First-party fixture's minimal accepted acknowledgment is `{"type":"response.created","response":{"id":"warm-1"}}` then `{"type":"response.completed","response":{"id":"warm-1", ...}}` ([fixture helpers](https://github.com/openai/codex/blob/8ff74cc9b11ac54c4c4446ef60a87b49ae657a1f/codex-rs/core/tests/common/responses.rs#L735-L775)). Production gateway frames should carry its normal complete Response shape and sequence metadata, while retaining these essentials.
4. **Warmup.** Codex sends normal `response.create` plus `generate:false`, with its actual prompt/tools/instructions, then waits for `response.completed`; it extracts that response ID and sends the generated turn with `previous_response_id:"warm-1"` and possibly `input:[]` on the **same socket** ([client.rs L1955-L2003](https://github.com/openai/codex/blob/8ff74cc9b11ac54c4c4446ef60a87b49ae657a1f/codex-rs/core/src/client.rs#L1955-L2003), [first-party two-request fixture](https://github.com/openai/codex/blob/8ff74cc9b11ac54c4c4446ef60a87b49ae657a1f/codex-rs/core/tests/suite/client_websockets.rs#L570-L643)). Thus warmup must validate/authenticate, retain a bounded connection-local snapshot, issue `response.created` and `response.completed` with the **same new ID**, and make **zero provider inference calls**. A mere silent acknowledgment, an `error`, or an ID without usable same-connection continuation fails this client. Official OpenAI Docs confirms no model output and a chainable response ID, but does not spell out the exact event pair; that pair is proven by this first-party fixture and reader ([official guide](https://developers.openai.com/api/docs/guides/websocket-mode.md)).
5. **Errors and recovery.** A top-level text frame `{"type":"error","status":400,"error":{"type":"invalid_request_error","code":"...","message":"..."}}` is the pinned reader's recognized status error envelope (`status_code` alias accepted); `error.code:"previous_response_not_found"` is explicitly mapped to retryable, even without status ([responses_websocket.rs L590-L661](https://github.com/openai/codex/blob/8ff74cc9b11ac54c4c4446ef60a87b49ae657a1f/codex-rs/codex-api/src/endpoint/responses_websocket.rs#L590-L661), [parser tests L1007-L1138](https://github.com/openai/codex/blob/8ff74cc9b11ac54c4c4446ef60a87b49ae657a1f/codex-rs/codex-api/src/endpoint/responses_websocket.rs#L1007-L1138)). For an accepted turn that fails during generation, send standard `response.failed` with nested `response.error`; never send `response.completed`. The first-party recovery fixture sends a failed second turn, then expects a third **full** `response.create` with no `previous_response_id` on a new socket ([client_websockets.rs L2253-L2380](https://github.com/openai/codex/blob/8ff74cc9b11ac54c4c4446ef60a87b49ae657a1f/codex-rs/core/tests/suite/client_websockets.rs#L2253-L2380)). Server must evict failed connection-local continuation and never expose partial output as reusable state. This recovery behavior is client source/fixture evidence, not a run against vNext.
6. **Overlap.** This Codex stream call serializes access to its socket until completion, so its fixture does not supply an overlapping-turn error schema ([responses_websocket.rs L278-L338](https://github.com/openai/codex/blob/8ff74cc9b11ac54c4c4446ef60a87b49ae657a1f/codex-rs/codex-api/src/endpoint/responses_websocket.rs#L278-L338)). The initial gateway should reject a second `response.create` while a turn is active with a **top-level recognized `error` frame**, e.g. `status:409` and nested `error:{type:"invalid_request_error",code:"...",message:"..."}`, leaving the first turn untouched. The exact overlap `code`/message is **not established by first-party source or official docs**; do not present a selected value as OpenAI compatibility. A concurrency fixture should assert no queueing, no second upstream call, and normal first-turn terminal, then a fresh turn succeeds.

## Acceptance fixture matrix before enabling `supports_websockets`

Use this pinned Codex checkout as the first-party fixture (or fetch the exact commit). No real account is required: local mock upstream and ephemeral gateway/key DB suffice. Verify handshake with the gateway-generated config; capture actual client frames. A successful loopback matrix includes: warmup event pair/ID and zero inference; generated continuation with empty delta; ordinary output and terminal-last; an immediate next turn after terminal/save; `response.failed` then full retry on a fresh connection; missing/evicted ID top-level error; scoped 426 causing one upgrade GET then HTTP POST; malformed/overlap error does not corrupt active turn; disabled key between turns; disconnect abort. Test Bun and Workers adapters separately. Prove memory/queue/send-buffer bounds with synthetic clients; the Codex client itself does not exercise malicious overlap or backpressure.

The current official guide's multiplexed `stream_id` and fork support is outside the single-turn bridge. Reject nontrivial multiplex/fork explicitly and advertise only tested ingress capability. The guide says `stream` is unused in WS mode while this pinned Codex serializer sends `stream:true`; accepting and ignoring that field is the narrow compatibility choice. No source here establishes exact close code/reason semantics for normal server shutdown or a normative overlap error code; do not gate first-slice delivery on invented values, but do gate a **claim of current-client compatibility** on the loopback fixture above.
